# SPIKE:

This machine is spike, the always-on NixOS home server that runs Bowerbird in production and doubles as a home lab, so every action here lands on production.
Its whole configuration is the `spike` host of the flake in `~/workspace/jimbo`, whose `.claude/CLAUDE.md` describes each service in detail and whose `modules/hosts/spike/` holds their modules; Bowerbird's own side is in `/srv/bowerbird/docs/spike.md`.
The system changes only through jimbo: a branch lands on its `main`, then `git pull && just` in `~/workspace/jimbo` switches to it, and anything set imperatively is lost or ignored by the next switch.
`jimbo-switch.timer` does that pull and switch as `aaron` within 5 minutes of `main` moving, while `~/workspace/jimbo` is on `main` with no uncommitted changes, and skips a commit whose switch already failed.
While Aaron is on a call, a switch or a `butler-pull` deploy that would restart butler or its speech services waits in butler's landing queue, `/var/lib/butler-land`, and goes at a quiet moment, when the call ends, on `land-queue now` or after 30 minutes, and a deploy that restarts butler also waits up to 10 minutes while one of its turns under 20 minutes old runs, so check `land-queue status` before assuming a landed commit is live.
`just` stages and builds whatever sits in `~/workspace/jimbo`, and work happens in worktrees.
Unattended switches of production spike are allowed, by a session that lands a jimbo branch.
`sudo` asks for no password, so nothing stands between a mistaken command and the live system.
`/srv/bowerbird` is Bowerbird's production checkout, which `bin/deploy` updates on every push to its `main`; checking out another branch there pauses deploys until `main` is checked out again.
`~/workspace/bowerbird` is a separate development checkout, and its branch databases live on the `postgresql` unit on `:5433`, beside `bowerbird_template`, which `bowerbird-template` clones from production at 03:30.
Its `bowerbird` role may create databases but is no superuser, holds `bowerbird_app` so the app's row-level security works, and has a password set by hand, kept in `~/.config/bowerbird/environment-password` for Bowerbird's `bin/env`.
`bowerbird-compose` runs production Postgres on `127.0.0.1:5432` and the portal on `:3000` in Docker, and `bowerbird-display` (the house's own `:99`, unwatched), `bowerbird-display@<N>` (one per signed-in member, its own display and VNC port), `bowerbird-vnc-proxy` (noVNC on `:6080`, routed per member by `?token=`) and `bowerbird-worker` run as the `bowerbird` user with state in `/var/lib/bowerbird`.
`bowerbird-sync-displays` keeps the proxy's token file and which `bowerbird-display@` instances run in sync with Postgres every minute.
`bowerbird-backup` dumps production into `/var/lib/bowerbird-backups` at 03:00.
Backlogic's `backlogic-aaron` runs backlogic's `compose.yaml` in Docker from the checkout `/srv/backlogic`, as `aaron` on the host's network on `:4200`, its store bind-mounted from `~/backlogic-data/aaron`, `backlogic-compose` runs `docker compose` for it, and Caddy serves it at `https://backlogic.spike.cute.engineer` over WireGuard.
`backlogic-switch` checks out backlogic's `main` in `/srv/backlogic` and rebuilds the container once `main` has moved and stayed put for 30 minutes while the instance's Windows Update installs automatically, or at once to the commit an owner chose there under *Let me choose*, and never checks out a commit that does not descend from the running one, since older code refuses a store newer code migrated.
After a switch it updates `aaron`'s installed backlogic plugin in `~/.claude` and `~/.claude-work`, and, when that update changed the rules the plugin prints and the plugin's commit is the one checked out, checks with `bin/rules-fresh-session` that a fresh session in each received them whole, a failure of which, or of the refresh, is logged and retried once on the next run without failing the unit.
Its runner, `backlogic-runner-aaron`, runs as the system user `backlogic-runner`, which has no `sudo`, from its own clones under `/var/lib/backlogic-runner/workspace` with mise's shims on its PATH, capped to 8G of memory, 2G of swap, 1024 tasks, 6 of the 8 threads and a fifth of the CPU weight, in its own cgroup namespace so its memory gate judges its own cap, killed alone by systemd-oomd if its cgroup stalls on memory and restarted by `butler-monitor` when it runs over `MemoryHigh` under critical pressure, at most every 30 minutes, and a switch never restarts it, since its sessions run inside it.
A session the runner launched runs as `backlogic-runner`, so it cannot run `sudo`, `just` or a switch, read `aaron`'s home or `~/workspace/jimbo`, or reach Docker, and it reaches `aaron` only to run Bowerbird's `bin/deploy`, and nothing else, as `ssh bowerbird-deploy`.
It lands a jimbo branch on `main` and stops there; Aaron, or a timer, deploys it.
`backlogic-sweep.timer` counts, read-only every 10 minutes as `backlogic-runner`, the tickets broken sessions left claimed, parked for the host, asking to run again, stuck in review, stale, or closed with unlanded work on their branch, for Grafana, and DMs Aaron the ones newly needing him.
`backlogic-source-instance` and `backlogic-source-runner` mirror the tracked source of the instance's and the runner's checkouts, read-only, into `/var/lib/backlogic-source` every 5 minutes, for butler and `butler-shell` to read.
`:4200` is open on `wlp2s0` and `wg0`.
`backlogic-tunnel` carries the instance's API, and only its `/api/`, to the public `https://backlogic-api.cute.engineer` through a Cloudflare Tunnel, by Caddy on `127.0.0.1:4201`, so the runner's cloud sessions on claude.ai reach it, every request still needing a session token, while the page stays on WireGuard.
Its token, from the tunnel made by hand in Cloudflare's Zero Trust dashboard, which also routes the hostname, is `/var/lib/secrets/cloudflared-backlogic-token`, and the unit skips starting until it exists.
The runner reads its cloud routine's API trigger token from `/var/lib/backlogic-runner-config/cloud-routine.token`, written by hand.
Caddy serves pilot's kanban board at `https://kanban.spike.cute.engineer` to `pilot`, the iPad, Aaron's phones, `piggys-MBP` and `jimbo` alone, behind the device gate's login but for the runners' bearer-token calls from `pilot`, `piggys-MBP` and `jimbo`, through `kanban-tunnel`, which runs `nc` to the board's loopback port on `pilot` over butler's ssh to it, `sudo device-gate-password` sets that login's password and signs every device out, and `sudo device-gate-revoke <peer>` signs one out.
The board is staged to move onto spike as `kanban.service`, the user `kanban` on `127.0.0.1:7420` with its state in `/var/lib/kanban/state`, served to Caddy by `kanban-bridge` in the tunnel's place while `/var/lib/kanban-hub/on-spike` exists, and `sudo kanban-hub scratch`, `cutover --yes` and `rollback` test, make and undo that move, copying pilot's state and never deleting it.
Aaron retired pilot's own board on 5 Nov 2026, so pilot's configuration no longer runs it, `cutover --yes` is the one-shot migration of its state, doing nothing once the marker exists, and nothing syncs pilot's board to spike.
Grafana, at `https://grafana.spike.cute.engineer` over WireGuard and `127.0.0.1:3001` locally, charts Prometheus on `:9090`, which scrapes node_exporter and cAdvisor and takes Claude Code metrics over OTLP, and its dashboards are provisioned from `modules/hosts/spike/dashboards.nix`, so any made in the UI are lost on the next switch.
Home Assistant serves `:8123` on the LAN and WireGuard alone, its secrets written by hand to `/var/lib/hass/secrets.yaml`, and its kiosk panel, a WallPanel screensaver of wallhaven wallpapers, the time, weather, and graphs of spike's hardware stats, Claude's plan limits and sessions, at `http://spike.local:8123/nixos-lovelace/panel`.
`wyoming-faster-whisper-en` and `wyoming-kokoro`, Kokoro's British `bm_lewis` voice, serve Home Assistant's Assist pipeline and butler's Discord calls on `127.0.0.1:10300` and `127.0.0.1:10200`, loopback only.
spike is `spike.local` on the LAN, `10.100.0.1` on WireGuard `wg0`, and `spike.cute.engineer` publicly, where WireGuard listens on UDP `51820`.
Claude Code runs here as `claude-remote-control`, serving `~/workspace` to claude.ai/code as `spike` on the work account in `~/.claude-work`, so restarting it, or a switch that changes `claude-code`, ends the sessions it hosts.
`butler` is Aaron's personal assistant bot, an instance of claude-discord-threads on the personal account, moving to Aaron's other accounts while it is at its limit, run as the system user `butler` from `/var/lib/butler/claude-discord-threads`, kept out of `/home`, and `butler-pull` deploys its `main` within 2 minutes.
Neither a switch nor `butler-pull` restarts `butler`: each writes `/run/butler-restart/wanted`, and the daemon restarts itself at once, or during a live call at its next quiet moment, at most about 10 minutes later, through `butler-restart.path`, while `butler-restart-overdue` restarts it once a wanted restart is 15 minutes old and the daemon is not deferring it.
Besides reading files and the web, it runs only the wrappers in `butler.commands`, for mail and sending it, calendar, Home Assistant devices short of locks, alarms and garage doors, reminders, Slack read-only, photos, its read-only personal data index, Aaron's reMarkable library, mirrored read-only from its cloud hourly by `butler-remarkable-sync`, pictures it renders or generates, kept with everything else it makes for Aaron in its asset store `/var/lib/butler/assets`, Google Drive, GitHub issues, backlogic tickets, Garmin, Hevy, its live feeds' status with Aaron's Steam library and Spotify plays, REVL's class timetable, with his bookings made in its own browser, Aaron's Obsidian vault, read and written, driving Aaron's MacBooks, working on Aaron's kanban board on `pilot`, its own memory, scheduled jobs, DMs to Aaron and changes made by cloud sessions, plus `shell`, which runs a script as the separate system user `butler-shell`, with the network and the journal but none of butler's files, and asks Aaron only before sending email or a Messenger message, acting through a session on that board, an outward action such as `shell` in a thread that read private data, or a write a voice request asked for, gathering waiting approvals into one DM to him every 15 seconds, while one approval for the kanban board, reminders, the calendar, home control, issues and tickets, `mac`, `shell` or `change` is a general permission for that area in the thread until `/revoke` or `/clear`, except that a `shell` script or `mac` action the daemon reads as sending to a person, paying, deleting or irreversibly changing data, or acting on `pilot` beyond reading asks every time, logged to `audit/shell` or `audit/mac` in its memory, unless a mission Aaron approved in that thread, one approval for a whole run naming its areas, machines and outcomes, sends to named recipients and payments to a named payee under a cap among them, covers it, after which nothing it lists asks and anything else asks once to extend it.
`tuwunel` is a Matrix homeserver on `127.0.0.1:6167` alone, with federation and registration off, and `mautrix-meta-facebook` bridges Aaron's Messenger into it, so butler's `messenger-*` wrappers, off until `butler.messenger.enable`, read and send it; `sudo messenger-setup` creates its user and logs the bridge in.
`butler-browser` runs its own Chromium as the user `butler-browser`, which it drives through Playwright MCP over DevTools on `127.0.0.1:9222`, a port the firewall resets for every other user but root, and which Aaron logs in to by hand at `https://browser.spike.cute.engineer`, while framer's panel only gets a view-only copy there.
`change`, once `self-fix`, which still works as its old name, queues Aaron's request in `/var/lib/butler/self-fix/queue`, and `butler-self-fix.path` starts a claude.ai cloud session on it as `aaron` from `~/workspace/jimbo`, on the personal account unless butler's account 1 is cooling down and on the work account then, which lands the change on `main` of jimbo, claude-discord-threads, butler-memory, butler or another of Aaron's repositories, and `butler-self-fix-progress` reads that session's state and recent activity from claude.ai as root, so butler never holds the token, for `change status` and every 2 minutes until it ends, DMing Aaron through `butler-notify`, with a mood picture by state, when it starts, ends or waits on him.
`butler-probe-runner` runs, as the sandboxed user `butler-probe` with no route to the LAN or WireGuard, the signed checks a live change session pushes to its `spike-probe/<id>` branch of butler-memory, and pushes their output back, logging each in `/var/lib/butler-probe-runner/log.jsonl`.
`butler-kanban-sync` keeps a card per change on that board every 2 minutes.
`butler-board-relay` carries Aaron's messages from that board's `/` popup into butler's spool `/var/lib/butler-board` every 3 seconds, where the daemon runs each as his own turn in a Discord thread, and carries the answers back.
`butler-builders` rebuilds, every 2 minutes and on every change's start or state change, the builders in flight digest of open and recent changes and Aaron's board sessions in the same repositories, which every new change gets after its brief and which it commits to `coordination/builders.md` in the private butler-memory alone.
`butler-context` rebuilds, every 5 minutes as root, butler's context packs in `/var/lib/butler-context`, one per area of Aaron's life from butler's memory, the builders digest, the kanban board and read-only facts about the work repositories on `pilot`, with anything private filtered out, which butler reads with `context` and kanban's `start_session` and `send_prompt` and every change brief start with.
`butler-work` turns the same records, every 2 minutes, into the plain-English snapshot `/var/lib/butler-work/work.json`, titles, one-line purposes, states, what needs Aaron and Claude account usage, for the life explorer's Work tab.
`butler-threads` writes, every 2 minutes as `butler`, the names, kinds, times and states of every Discord thread butler has, never what was said, to `/var/lib/butler-threads/threads.json`, for the life explorer's Threads tab.
`butler-monitor` watches spike, framer, both Macs and the jimbo PC every 2 minutes as root, reading the Macs and the PC over short read-only ssh calls, DMs Aaron or shouts into his call, once, only about new or worsened problems he can act on, such as disk, memory, extreme load, battery, keep-awake, failed units or every Claude account spent, never about a machine marked expected off with `monitor expect` or put to sleep with `mac`, and takes only its own safe clean-ups, keep-awake, restarts of listed failed units and, for critical memory pressure, a full disk or runaway load, the remediations listed in `butler-monitor/defaults.nix`, never touching butler, Home Assistant, Docker, sshd or WireGuard, naming the biggest memory cgroup in every memory notice, in `dry-run` until `monitor act on`, logging what it told and kept quiet to `/var/lib/butler-monitor/notices.jsonl` and its actions to `actions.jsonl`.
`remote-desk` is Aaron's web remote desktop for his iPad at `https://desk.spike.cute.engineer` over WireGuard, opening each Mac's or the jimbo PC's screen through its own restricted ssh key, behind the same device gate login, so `sudo device-gate-revoke <peer>` also ends that device's screens, logged under `journalctl -u remote-desk`.
`butler-memory-pull` mirrors its memory, `kranners/butler-memory`, into `/var/lib/butler/memory` every 5 minutes, and the daemon runs the scheduled prompts in `/var/lib/butler/cron`: links to that memory's `cron`, made by `butler-jobs.timer`, beside the jobs butler adds with its `jobs` command, which DM Aaron their result through `notify`, or end their reply with `NOTHING` when there is nothing new, so the daemon deletes the run's thread and sends nothing.
`butler-notify`, run by `aaron` or anything in the group `butler-notify`, has butler DM Aaron its stdin and any files named, through the spool `/var/lib/butler-notify`.
`butler-inbox` polls Aaron's mail inboxes as `butler` every 90 seconds, has Haiku with no tools label each new message, and DMs him what matters through that spool, a few pings a day, an 18:30 digest and only urgent ones from 22:00 to 07:00, logging everything to the append-only audit log in `/var/lib/butler-inbox/inbox.db`, which butler's `inbox` reads; `/inbox off` in butler's DM stops it.
Once `butler.voice.enable` is on, butler also answers framer's Assist pipeline, through Home Assistant's llama.cpp integration, on `127.0.0.1:18789`, with the bearer token in `/var/lib/secrets/butler-voice-token`.
It logs each voice request and its answer to `/var/lib/butler/voice-log/YYYY-MM-DD.md`.
Once its daemon on `main` serves calls, it also joins a Discord voice channel on Aaron's `/call`, hearing him through `wyoming-faster-whisper-en` and answering aloud through `wyoming-kokoro`, with every ability it has in a thread, in the Jeeves-like voice of `butler-call.md`, answering small talk and quick lookups such as the time, agenda, reminders, maps and the board at once with Haiku in `butler-call-fast.md` and handing real work to the full session, which runs on Sonnet at low effort during a call and speaks as it streams, and posting a call's text without notifications.
In front of that, OpenAI's realtime voice, `gpt-realtime-2.1` with `butler-call-realtime.md`, the full Butler's command list, butler's memory's `core/character.md` and the voice brief `butler-voice-style.md`, hears calls and answers in text that `wyoming-kokoro` speaks in `bm_lewis`, or speech to speech in an OpenAI voice if `/realtime voice` picks one, with the same lookups, handing everything else, changes included, to the full session, using the imagine key in `/var/lib/secrets/butler-openai-api-key`, capped at 10 dollars a month, and falls back to Kokoro and Haiku when OpenAI refuses or the cap is spent; `butler.voice.realtime.enable = false` turns it off.
`aaron`'s `~/.claude` is the personal `aaron@cute.engineer` account, and backlogic's runner, logged in to both accounts under its own home, spends personal first and moves to the work account only while personal is at its limit.
python3 is installed system-wide because Claude Code hooks in repositories here run with it, and one that fails to start is treated as allowing the call, so a guard without it refuses nothing.
google-chrome is installed system-wide because backlogic's `bin/check` and its board publishing load each board in a headless Chrome they find on PATH, and refuse without one.
Secrets are written by hand and never printed, committed or sent anywhere: `/srv/bowerbird/.env`, `~/.claude/.credentials.json`, `~/.claude-work/.credentials.json`, `~/.claude/channels/discord/.env`, `~/.ssh/claude-discord-threads-deploy`, `/var/lib/butler/.ssh/claude-discord-threads-deploy`, `/var/lib/butler/.local/share/pyicloud`, `/var/lib/butler/.claude-accounts`, `/var/lib/butler/.local/share/ortie`, `/var/lib/butler/.local/share/work-google`, `/var/lib/butler/.config/rclone`, `/var/lib/butler/.cache`, `/var/lib/butler-browser/profile`, `/var/lib/butler-index`, `/var/lib/butler-feeds`, `/var/lib/butler-notes/config`, `/var/lib/hass/secrets.yaml`, `/var/lib/grafana/backlogic-token`, `~/.config/bowerbird/environment-password`, `/var/lib/backlogic-runner-config/cloud-routine.token`, `/var/lib/remote-desk`, `/var/lib/secrets/` and `/var/lib/wireguard/private`.
`/var/lib/tuwunel`, `/var/lib/matrix-double-puppet` and `/var/lib/mautrix-meta-facebook` hold Matrix tokens, the Facebook session and decrypted messages, and are never printed or sent anywhere either.
`/var/lib/butler-index` holds Aaron's personal data index, his payments, location history, conversations and more, owned by `butler`, written by the `butler-index-*`, `butler-notes-sync`, `butler-photo-caption` and `butler-remarkable-sync` units, the last into its `remarkable` folder, and read by butler's `life` and `remarkable`, by `life-explorer`, which Caddy serves at `https://life.spike.cute.engineer`, and by `butler-money`, the finance dashboard at `https://life.spike.cute.engineer/money/` (`money.spike.cute.engineer` redirects there) whose debts and decisions live in `/var/lib/butler-money/plan.json`, both to `piggys-MBP`, `phone`, `phone-2` and `pilot` alone, and to the iPad once the device gate has signed it in, all from the private flake `kranners/butler`, whose `CLAUDE.md` says what each inbox folder takes; exports go into its `inbox/<folder>` folders with `sudo cp`, left readable to `butler`.
butler's `mac <host> fetch` copies a file from `piggys-MBP`'s or jimbo's `~/Downloads` or `~/butler-drop` into the same folders, through `butler-index-drop`, which moves it in from `/var/lib/butler/.cache/index-drop/spool`, and `inbox/exports` holds statements and service exports, which the ingest reads into `hostplus`, `spaceship`, `goodreads`, `letterboxd`, `linkedin` and `exports`.
`/var/lib/butler-daily` holds Aaron's daily dashboards, one JSON and one PNG a day of his calendar, work status, mail senders and plans, owned by `butler`, written by butler's `daily` command and `butler-daily-render` and read by `life-explorer`'s Daily tab, so it is never printed or copied off spike.
The system user `browser-history` writes to the index only through `butler-browser-history-drop`, run as `butler` by its one sudo rule, which can only rename a validated `<device>-<browser>-<profile>.sqlite` snapshot into `inbox/browser` or `<device>-messages.sqlite` snapshot of Aaron's texts into `inbox/messages`.
`butler-feeds` fetches, hourly as `butler`, Letterboxd's and Goodreads' public RSS, Spotify, Steam and PayPal once `sudo butler-feeds-login <feed>` has stored a login, and Hostplus, CMC, Uber and Amazon mail, into the index inbox in its exports' shapes, and `sudo butler-slack-login` writes butler's live Slack token.
`butler-notes-sync` mirrors Aaron's Obsidian vault from Obsidian Sync, download only, into `/var/lib/butler-notes/vault` every 15 minutes, which butler reads read-only, once Aaron has run `sudo -u butler butler-notes-login Latte`, its login kept in `/var/lib/butler-notes/config`.
`butler-notes-write` applies butler's `note` writes to that vault and pushes them through the same login, never deleting, committing each note before and after to `/var/lib/butler-notes/history.git`, from which `note restore` undoes one, and logging each to `/var/lib/butler-notes/writes.jsonl`.
It has 8 threads, 15 GiB of memory with half as much again of zram swap, and a 233 GB NVMe disk, never sleeps, and reboots itself through a hardware watchdog when it hangs and 10 s after a kernel panic.
