# SPIKE:

This machine is spike, the always-on NixOS home server that runs Bowerbird in production and doubles as a home lab, so every action here lands on production.
Its whole configuration is the `spike` host of the flake in `~/workspace/jimbo`, whose `.claude/CLAUDE.md` describes each service in detail and whose `modules/hosts/spike/` holds their modules; Bowerbird's own side is in `/srv/bowerbird/docs/spike.md`.
The system changes only through jimbo: a branch lands on its `main`, then `git pull && just` in `~/workspace/jimbo` switches to it, and anything set imperatively is lost or ignored by the next switch.
`jimbo-switch.timer` does that pull and switch as `aaron` within 5 minutes of `main` moving, while `~/workspace/jimbo` is on `main` with no uncommitted changes, and skips a commit whose switch already failed.
`just` stages and builds whatever sits in `~/workspace/jimbo`, and work happens in worktrees.
Unattended switches of production spike are allowed, by a session that lands a jimbo branch.
`sudo` asks for no password, so nothing stands between a mistaken command and the live system.
`/srv/bowerbird` is Bowerbird's production checkout, which `bin/deploy` updates on every push to its `main`; checking out another branch there pauses deploys until `main` is checked out again.
`~/workspace/bowerbird` is a separate development checkout, and its branch databases live on the `postgresql` unit on `:5433`, beside `bowerbird_template`, which `bowerbird-template` clones from production at 03:30.
Its `bowerbird` role may create databases but is no superuser, holds `bowerbird_app` so the app's row-level security works, and has a password set by hand, kept in `~/.config/bowerbird/environment-password` for Bowerbird's `bin/env`.
`bowerbird-compose` runs production Postgres on `127.0.0.1:5432` and the portal on `:3000` in Docker, and `bowerbird-display` (the house's own `:99`, unwatched), `bowerbird-display@<N>` (one per signed-in member, its own display and VNC port), `bowerbird-vnc-proxy` (noVNC on `:6080`, routed per member by `?token=`) and `bowerbird-worker` run as the `bowerbird` user with state in `/var/lib/bowerbird`.
`bowerbird-sync-displays` keeps the proxy's token file and which `bowerbird-display@` instances run in sync with Postgres every minute.
`bowerbird-backup` dumps production into `/var/lib/bowerbird-backups` at 03:00.
Backlogic's `backlogic-aaron` runs backlogic's `compose.yaml` in Docker from the checkout `/srv/backlogic`, as `aaron` on the host's network on `:4200`, its store bind-mounted from `~/backlogic-data/aaron`, `backlogic-compose` runs `docker compose` for it, and Caddy serves it at `https://backlogic.spike.cute.engineer` over WireGuard.
`backlogic-switch` checks out backlogic's `main` in `/srv/backlogic` and rebuilds the container once `main` has moved and stayed put for 30 minutes while the instance's Windows Update installs automatically, or at once to the commit an owner chose there under *Let me choose*, and never checks out a commit that does not descend from the running one, since older code refuses a store newer code migrated.
After a switch it updates `aaron`'s installed backlogic plugin in `~/.claude` and `~/.claude-work`, and, when that update changed the rules the plugin prints and the plugin's commit is the one checked out, checks with `bin/rules-fresh-session` that a fresh session in each received them whole.
Its runner, `backlogic-runner-aaron`, runs as the system user `backlogic-runner`, which has no `sudo`, from its own clones under `/var/lib/backlogic-runner/workspace` with mise's shims on its PATH, capped to 8G of memory and 2G of swap and a fifth of the CPU weight, and a switch never restarts it, since its sessions run inside it.
A session the runner launched runs as `backlogic-runner`, so it cannot run `sudo`, `just` or a switch, read `aaron`'s home or `~/workspace/jimbo`, or reach Docker, and it reaches `aaron` only to run Bowerbird's `bin/deploy`, and nothing else, as `ssh bowerbird-deploy`.
It lands a jimbo branch on `main` and stops there; Aaron, or a timer, deploys it.
`backlogic-sweep.timer` counts, read-only every 10 minutes as `backlogic-runner`, the tickets broken sessions left claimed, parked for the host, asking to run again, stuck in review, stale, or closed with unlanded work on their branch, for Grafana, and DMs Aaron the ones newly needing him.
`:4200` is open on `wlp2s0` and `wg0`.
`backlogic-tunnel` carries the instance's API, and only its `/api/`, to the public `https://backlogic-api.cute.engineer` through a Cloudflare Tunnel, by Caddy on `127.0.0.1:4201`, so the runner's cloud sessions on claude.ai reach it, every request still needing a session token, while the page stays on WireGuard.
Its token, from the tunnel made by hand in Cloudflare's Zero Trust dashboard, which also routes the hostname, is `/var/lib/secrets/cloudflared-backlogic-token`, and the unit skips starting until it exists.
The runner reads its cloud routine's API trigger token from `/var/lib/backlogic-runner-config/cloud-routine.token`, written by hand.
Grafana, at `https://grafana.spike.cute.engineer` over WireGuard and `127.0.0.1:3001` locally, charts Prometheus on `:9090`, which scrapes node_exporter and cAdvisor and takes Claude Code metrics over OTLP, and its dashboards are provisioned from `modules/hosts/spike/dashboards.nix`, so any made in the UI are lost on the next switch.
Home Assistant serves `:8123` on the LAN and WireGuard alone, its secrets written by hand to `/var/lib/hass/secrets.yaml`, and its kiosk panel, a WallPanel screensaver of wallhaven wallpapers, the time, weather, and graphs of spike's hardware stats, Claude's plan limits and sessions, at `http://spike.local:8123/nixos-lovelace/panel`.
`wyoming-faster-whisper-en` and `wyoming-kokoro`, Kokoro's British `bm_lewis` voice, serve Home Assistant's Assist pipeline and butler's Discord calls on `127.0.0.1:10300` and `127.0.0.1:10200`, loopback only.
spike is `spike.local` on the LAN, `10.100.0.1` on WireGuard `wg0`, and `spike.cute.engineer` publicly, where WireGuard listens on UDP `51820`.
Claude Code runs here as `claude-remote-control`, serving `~/workspace` to claude.ai/code as `spike` on the work account in `~/.claude-work`, so restarting it, or a switch that changes `claude-code`, ends the sessions it hosts.
`butler` is Aaron's personal assistant bot, an instance of claude-discord-threads on the personal account, moving to Aaron's other accounts while it is at its limit, run as the system user `butler` from `/var/lib/butler/claude-discord-threads`, kept out of `/home`, and `butler-pull` deploys its `main` within 2 minutes.
Neither a switch nor `butler-pull` restarts `butler`: each writes `/run/butler-restart/wanted`, and the daemon restarts itself at once, or during a live call at its next quiet moment, at most about 10 minutes later, through `butler-restart.path`, while `butler-restart-overdue` restarts it once a wanted restart is 15 minutes old and the daemon is not deferring it.
Besides reading files and the web, it runs only the wrappers in `butler.commands`, for mail and sending it, calendar, Home Assistant devices short of locks, alarms and garage doors, reminders, Slack read-only, photos, its read-only personal data index, Aaron's reMarkable library, mirrored read-only from its cloud hourly by `butler-remarkable-sync`, pictures it renders or generates, Google Drive, GitHub issues, backlogic tickets, Garmin, Hevy, driving Aaron's MacBooks, working on Aaron's kanban board on `pilot`, its own memory, scheduled jobs, DMs to Aaron and fixes to itself, plus `shell`, which runs a script as the separate system user `butler-shell`, with the network and the journal but none of butler's files, and asks Aaron only before sending email or a Messenger message, acting through a session on that board, an outward action such as `shell` in a thread that read private data, or a write a voice request asked for, gathering waiting approvals into one DM to him every 15 seconds.
`tuwunel` is a Matrix homeserver on `127.0.0.1:6167` alone, with federation and registration off, and `mautrix-meta-facebook` bridges Aaron's Messenger into it, so butler's `messenger-*` wrappers, off until `butler.messenger.enable`, read and send it; `sudo messenger-setup` creates its user and logs the bridge in.
`butler-browser` runs its own Chromium as the user `butler-browser`, which it drives through Playwright MCP over DevTools on `127.0.0.1:9222`, a port the firewall resets for every other user but root, and which Aaron logs in to by hand at `https://browser.spike.cute.engineer`, while framer's panel only gets a view-only copy there.
`self-fix` queues Aaron's request in `/var/lib/butler/self-fix/queue`, and `butler-self-fix.path` starts a claude.ai cloud session on it as `aaron` from `~/workspace/jimbo`, on the personal account unless butler's account 1 is cooling down and on the work account then, which lands the fix on `main` of jimbo, claude-discord-threads, butler-memory or butler, and `butler-self-fix-progress` reads that session's state and recent activity from claude.ai as root, so butler never holds the token, for `self-fix status` and every 2 minutes until it ends, DMing Aaron through `butler-notify`, with a mood picture by state, when it starts, ends or waits on him.
`butler-probe-runner` runs, as the sandboxed user `butler-probe` with no route to the LAN or WireGuard, the signed checks a live self-fix session pushes to its `spike-probe/<id>` branch of butler-memory, and pushes their output back, logging each in `/var/lib/butler-probe-runner/log.jsonl`.
`butler-kanban-sync` keeps a card per self-fix on that board every 2 minutes.
`butler-builders` rebuilds, every 2 minutes and on every self-fix start or state change, the builders in flight digest of open and recent self-fixes and Aaron's board sessions in the same repositories, which every new self-fix gets after its brief and which it commits to `coordination/builders.md` in the private butler-memory alone.
`butler-memory-pull` mirrors its memory, `kranners/butler-memory`, into `/var/lib/butler/memory` every 5 minutes, and the daemon runs the scheduled prompts in `/var/lib/butler/cron`: links to that memory's `cron`, made by `butler-jobs.timer`, beside the jobs butler adds with its `jobs` command, which DM Aaron their result through `notify`.
`butler-notify`, run by `aaron` or anything in the group `butler-notify`, has butler DM Aaron its stdin and any files named, through the spool `/var/lib/butler-notify`.
Once `butler.voice.enable` is on, butler also answers framer's Assist pipeline, through Home Assistant's llama.cpp integration, on `127.0.0.1:18789`, with the bearer token in `/var/lib/secrets/butler-voice-token`.
It logs each voice request and its answer to `/var/lib/butler/voice-log/YYYY-MM-DD.md`.
Once its daemon on `main` serves calls, it also joins a Discord voice channel on Aaron's `/call`, hearing him through `wyoming-faster-whisper-en` and answering aloud through `wyoming-kokoro`, with every ability it has in a thread, in the Jeeves-like voice of `butler-call.md`, answering small talk and quick lookups such as the time, agenda, reminders, maps and the board at once with Haiku in `butler-call-fast.md` and handing real work to the full session, which runs on Sonnet at low effort during a call and speaks as it streams, and posting a call's text without notifications.
In front of that, OpenAI's realtime voice, `gpt-realtime-2.1` with `butler-call-realtime.md`, the full Butler's command list, butler's memory's `core/character.md` and the voice brief `butler-voice-style.md`, hears calls and answers in text that `wyoming-kokoro` speaks in `bm_lewis`, or speech to speech in an OpenAI voice if `/realtime voice` picks one, with the same lookups, handing everything else, self-fixes included, to the full session, using the imagine key in `/var/lib/secrets/butler-openai-api-key`, capped at 10 dollars a month, and falls back to Kokoro and Haiku when OpenAI refuses or the cap is spent; `butler.voice.realtime.enable = false` turns it off.
`aaron`'s `~/.claude` is the personal `aaron@cute.engineer` account, and backlogic's runner, logged in to both accounts under its own home, spends personal first and moves to the work account only while personal is at its limit.
python3 is installed system-wide because Claude Code hooks in repositories here run with it, and one that fails to start is treated as allowing the call, so a guard without it refuses nothing.
google-chrome is installed system-wide because backlogic's `bin/check` and its board publishing load each board in a headless Chrome they find on PATH, and refuse without one.
Secrets are written by hand and never printed, committed or sent anywhere: `/srv/bowerbird/.env`, `~/.claude/.credentials.json`, `~/.claude-work/.credentials.json`, `~/.claude/channels/discord/.env`, `~/.ssh/claude-discord-threads-deploy`, `/var/lib/butler/.ssh/claude-discord-threads-deploy`, `/var/lib/butler/.local/share/pyicloud`, `/var/lib/butler/.claude-accounts`, `/var/lib/butler/.local/share/ortie`, `/var/lib/butler/.config/rclone`, `/var/lib/butler/.cache`, `/var/lib/butler-browser/profile`, `/var/lib/butler-index`, `/var/lib/butler-notes/config`, `/var/lib/hass/secrets.yaml`, `/var/lib/grafana/backlogic-token`, `~/.config/bowerbird/environment-password`, `/var/lib/backlogic-runner-config/cloud-routine.token`, `/var/lib/secrets/` and `/var/lib/wireguard/private`.
`/var/lib/tuwunel`, `/var/lib/matrix-double-puppet` and `/var/lib/mautrix-meta-facebook` hold Matrix tokens, the Facebook session and decrypted messages, and are never printed or sent anywhere either.
`/var/lib/butler-index` holds Aaron's personal data index, his payments, location history, conversations and more, owned by `butler`, written by the `butler-index-*`, `butler-notes-sync`, `butler-photo-caption` and `butler-remarkable-sync` units, the last into its `remarkable` folder, and read by butler's `life` and `remarkable`, by `life-explorer`, which Caddy serves at `https://life.spike.cute.engineer`, and by `butler-money`, the finance dashboard at `https://life.spike.cute.engineer/money/` (`money.spike.cute.engineer` redirects there) whose debts and decisions live in `/var/lib/butler-money/plan.json`, both to `piggys-MBP`, `phone`, `phone-2` and `pilot` alone, all from the private flake `kranners/butler`, whose `CLAUDE.md` says what each inbox folder takes; exports go into its `inbox/<folder>` folders with `sudo cp`, left readable to `butler`.
The system user `browser-history` writes to the index only through `butler-browser-history-drop`, run as `butler` by its one sudo rule, which can only rename a validated `<device>-<browser>-<profile>.sqlite` snapshot into `inbox/browser` or `<device>-messages.sqlite` snapshot of Aaron's texts into `inbox/messages`.
`butler-notes-sync` mirrors Aaron's Obsidian vault from Obsidian Sync, download only, into `/var/lib/butler-notes/vault` every 15 minutes, which butler reads read-only, once Aaron has run `sudo -u butler butler-notes-login Latte`, its login kept in `/var/lib/butler-notes/config`.
It has 8 threads, 15 GiB of memory with half as much again of zram swap, and a 233 GB NVMe disk, never sleeps, and reboots itself through a hardware watchdog when it hangs and 10 s after a kernel panic.
